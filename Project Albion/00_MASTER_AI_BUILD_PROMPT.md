## Decisions already made

### Multiplayer
- Exactly two human managers are required for v1.
- One authoritative server owns all canonical state.
- Clients are UI/input clients and never authoritatively resolve transfers, contracts, results, game-time advancement or finances.
- Private LAN or trusted private network such as Tailscale is the intended connection model.
- No public matchmaking, cloud account, ranking, telemetry or monetization.
- One host session + one guest.
- Each human must control a different English club.

### Football world
Fully playable:
- Premier League
- Championship
- League One
- League Two

Background/feeder simulation:
- National League and lower English clubs sufficient for relegation, promotion and cup participants.
- foreign clubs/leagues sufficient for transfer market and continental competition.

Domestic competition minimum:
- league competitions above
- FA Cup
- EFL Cup
- Community Shield where applicable

Continental minimum for qualifying English clubs:
- Champions League-style competition
- Europa League-style competition
- Conference League-style competition

Competition details must come from versioned season rulesets, not permanent constants.

### Real data model: Season Reset
The canonical new-career mode is intentionally an alternate timeline.

1. Import real club/player roster facts up to an operator-selected freeze date, normally after a transfer window closes.
2. Publish an immutable snapshot.
3. Create a new career from that snapshot.
4. Reset league tables, season statistics and match results to zero.
5. Begin the simulated season with the post-window squads.
6. From that moment, every result, transfer, injury, contract, development event, manager event, table and trophy is generated by Project Albion.
7. Updating the real-world snapshot later must never mutate an existing career.

Do not import real match results into Season Reset.

### Match engine
- Server-authoritative.
- Explicit seed and engine version.
- Deterministic for identical input + seed + version.
- One shared match state for human-v-human.
- Supports instant AI-v-AI and interactive live matches.
- No database/network I/O inside engine.
- No wall-clock randomness.
- Project Albion owns gameplay ratings and simulation logic.

### Language
- English is canonical development locale.
- Thai (`th-TH`) is a first-class shipping locale.
- All user-visible text uses i18n keys.

## Required boundaries

### Domain
Pure football entities, invariants and value types. No Tauri/React/HTTP/WebSocket.

### Engine
Consumes immutable match input; accepts explicit RNG seed; emits events/report. No DB, network or real clock.

### Core
Owns calendar/day processing and coordinates competitions, transfers, finances, training, scouting, injuries, AI and match results.

### DB
Relational per-career persistence with migrations, transactions, backup and integrity checks.

### Server
Owns canonical state, validates commands, serializes mutation, advances time, broadcasts versioned updates, persists critical actions.

### Client
Presentation, user input, local preferences and cache. Canonical changes require server acknowledgement.

### Data pipeline
Offline/manual maintenance tool. Imports, normalizes, resolves identity, validates, diffs and publishes immutable snapshots. Never updates active careers.

## State/version rules

Persist independent versions:
- `app_version`
- `save_schema_version`
- `snapshot_schema_version`
- `protocol_version`
- `match_engine_version`
- `ruleset_version`
- `rating_model_version`

Every career records its source snapshot and relevant versions.

Old saves migrate safely or fail non-destructively with a clear compatibility error. Never silently reinterpret old state.

## Core gameplay loop

```text
Host/load career
→ manage inbox/squad/training/scouting/transfers
→ set tactics/selection
→ both managers Ready
→ server advances until next blocker
→ play/watch fixtures
→ apply results/injuries/finance/news/tables
→ repeat
→ season rollover
→ promotion/relegation/cups/continental qualification
→ offseason/window
→ next season
```

A blocker is something requiring human action: invalid lineup, required registration, human match kickoff, deadline response or explicit stop point. Do not stop for routine AI-only events.

## No fabricated facts

Never invent a real player's club, date of birth, nationality, contract or transfer.

Unknown source facts remain NULL/unknown.

Generated gameplay attributes are explicitly game-owned, for example:
`attribute_origin = albion_rating_v1`.

## Engineering priorities

In order:
1. correct state transitions;
2. save safety;
3. deterministic match behavior;
4. multiplayer convergence/reconnect;
5. competent AI managers;
6. complete management loop;
7. usable dense UI;
8. polish.

Avoid:
- microservices;
- Kubernetes;
- public cloud accounts;
- always-online DRM;
- 3D match rendering;
- mobile/console scope;
- required LLM/API dependency.

Optional generated news can come later and must never control game state.
